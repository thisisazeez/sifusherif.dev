What is multi-tenancy, actually

Multi-tenancy means one running application serves multiple customers (tenants), and each customer's data is isolated from every other customer's data. If you're building a SaaS product — a project management tool, a CRM, a co-working management system — you probably need some form of this.

There are three common approaches:

  • Shared database, shared schema — all tenants in the same tables, with a tenant_id column on every row. Simple to implement, hard to get right, easy to accidentally leak data.
  • Shared database, separate schemas — one database, but each tenant gets their own set of tables inside a PostgreSQL schema. This is what django-tenants does.
  • Separate databases — one database per tenant. Maximum isolation, maximum operational complexity.

django-tenants implements the middle option — separate schemas within one PostgreSQL database. If you're on MySQL or SQLite, stop reading and choose a different approach. django-tenants requires PostgreSQL. This is in the documentation, but not in the part of the documentation you read first.

What django-tenants actually does

When you install django-tenants and create a tenant, it creates a new PostgreSQL schema for that tenant and runs your tenant-aware migrations inside that schema. Each tenant gets a complete, private copy of all tenant-aware tables.

There's also a public schema — the default PostgreSQL schema — where shared data lives: the tenant list, authentication tables if you share auth across tenants, any data that belongs to the application rather than to any specific tenant.

The distinction between public-schema models and tenant-schema models is the first thing that will confuse you. Every model in your application belongs to one of these two categories, and you configure that by controlling which apps are in SHARED_APPS vs TENANT_APPS in your settings.

When a request comes in, a middleware reads the subdomain (or whatever routing strategy you've configured) and sets the correct PostgreSQL schema for that request. All database queries in that request then run against that tenant's schema automatically.

The SHARED_APPS / TENANT_APPS split

This is where most people — including me — get confused initially. Here's what the settings look like:

SHARED_APPS = [
    'django_tenants',
    'django.contrib.contenttypes',
    'django.contrib.auth',
    'myapp.tenants',   # the Tenant model lives here
    'myapp.accounts',  # shared auth
]

TENANT_APPS = [
    'django.contrib.sessions',
    'myapp.workspaces',   # tenant-specific data
    'myapp.billing',
    'myapp.bookings',
]

INSTALLED_APPS = list(SHARED_APPS) + [
    app for app in TENANT_APPS if app not in SHARED_APPS
]

The critical rules:

  • Every app in SHARED_APPS runs migrations in the public schema only
  • Every app in TENANT_APPS runs migrations in every tenant schema
  • Apps can be in both lists — their migrations run in both public and tenant schemas
  • django_tenants itself must be first in SHARED_APPS

The confusion I ran into: I had a users app that I wanted in both schemas — a global users table in public, but per-tenant user profile extensions in tenant schemas. The solution is to split this into two apps: accounts (shared, has the base User model) and profiles (tenant-only, has the profile extension).

Routing — how Django knows which schema to use

The default routing strategy uses subdomains. acme.yourapp.com routes to the "acme" tenant. globex.yourapp.com routes to "globex". The middleware does the subdomain parsing and sets the active schema before your view runs.

MIDDLEWARE = [
    'django_tenants.middleware.main.TenantMainMiddleware',
    # ... rest of your middleware
]

# In your Tenant model
class Tenant(TenantMixin):
    name = models.CharField(max_length=100)

    auto_create_schema = True  # creates the schema on save

The part the docs underexplain: auto_create_schema = True means that when you .save() a new Tenant object, django-tenants automatically creates the PostgreSQL schema and runs all tenant migrations in it. This is convenient but means your tenant creation can fail midway through migration — you want this inside a transaction and with error handling.

Running migrations

You'll use two management commands instead of the standard migrate:

# Run shared (public schema) migrations
python manage.py migrate_schemas --shared

# Run tenant migrations across all tenant schemas
python manage.py migrate_schemas --tenant

# Run both
python manage.py migrate_schemas

The behaviour that will catch you: if you run python manage.py migrate (the standard command) in a django-tenants project, it won't do what you expect. Always use migrate_schemas.

The things that will break your production app

After working with this in a real project, these are the edge cases I wish someone had written down:

Raw SQL queries and django.db.connection.cursor() bypass the schema routing entirely. If you have any raw SQL — including in third-party packages — it will hit whatever schema is set at the database level, not necessarily the active tenant's schema. Audit your dependencies for raw queries before deploying.

  • Celery tasks don't automatically inherit the active schema. When a request triggers a Celery task, the task runs in a new context with no schema set. You must explicitly pass the tenant identifier to the task and set the schema at the start of the task.
  • The public schema is not a safe default. Several Django internals (sessions, content types) behave unexpectedly when accessed from a tenant schema context. Keep a clear mental model of what lives where.
  • Cross-tenant queries require caution. If you need to query across all tenants — for admin purposes, analytics, billing — you need to either iterate through tenants and switch schemas, or use raw SQL with schema-qualified table names.
  • New tenant schema creation is slow if you have many migrations. On a project with 200 migrations, creating a new tenant and running all migrations takes 15–30 seconds. Consider this in your onboarding flow.

When not to use django-tenants

Schema-per-tenant is the right choice for a specific set of requirements. It's probably wrong for your project if:

  • You're not using PostgreSQL and can't switch
  • You have hundreds of thousands of tenants — managing that many schemas becomes an operational problem
  • Your tenants frequently need to query each other's data — cross-schema queries are painful
  • You're early stage and the isolation requirements of schema separation are overkill — a well-implemented tenant_id column approach is much simpler and sufficient for most early SaaS products

For what it's worth: I used django-tenants on a project where it was the right choice, and the isolation guarantees it provides are genuinely valuable. When you're handling data for multiple businesses that have regulatory requirements around data separation, knowing that it's physically impossible for tenant A's query to touch tenant B's tables is meaningful. Just go in with clear eyes about the complexity it adds.
