Start with the problem, not the solution

Every system design exercise goes wrong the same way: someone names a technology before they've understood the problem. "We'll use Kafka." "We'll shard the database." These might be right answers — but to questions that haven't been asked yet.

So let's start with what Twitter's timeline actually needs to do. When you open Twitter and see your feed, the system has to answer one question: what are the most recent tweets from the people I follow, in reverse chronological order?

That sounds simple. The problem is the scale at which it has to be answered — hundreds of millions of users, each following a different set of people, each expecting their feed to load in under 100ms, while roughly 6,000 new tweets are posted every second.

The naive approach — and why it doesn't work

Before reaching for a sophisticated solution, consider the obvious one. When a user loads their timeline, query the database:

-- The query that would work at small scale
SELECT tweets.*
FROM tweets
JOIN follows ON tweets.user_id = follows.followed_id
WHERE follows.follower_id = :current_user_id
ORDER BY tweets.created_at DESC
LIMIT 20;

This works. If you're building a side project with 500 users, do this. It's simple, correct, and maintainable.

At Twitter's scale, it doesn't work for two reasons. First, the follows table has billions of rows. The join is expensive. Second, and more fundamentally, this query runs at read time — every time someone opens their feed. If a million users open Twitter simultaneously, a million of these expensive joins run at the same moment.

Fan-out on write

Twitter's original solution — and still the core approach — is called fan-out on write. The idea: instead of computing each user's timeline at read time, compute it at write time. When a tweet is posted, immediately push it into the timeline cache of every follower.

Each user has a timeline stored in Redis — a sorted set, where the score is the tweet's timestamp and the member is the tweet ID. When you post a tweet:

# Pseudocode — what happens when @someone posts a tweet
def on_tweet_posted(tweet):
    followers = get_followers(tweet.author_id)  # could be millions

    for follower_id in followers:
        redis.zadd(
            f"timeline:{follower_id}",
            {tweet.id: tweet.created_at.timestamp()}
        )
        # Trim to last 800 tweets to cap memory
        redis.zremrangebyrank(f"timeline:{follower_id}", 0, -801)

Then reading the timeline is trivially fast — just read the sorted set:

# Reading a user's timeline — fast, no joins
def get_timeline(user_id, page=0, per_page=20):
    tweet_ids = redis.zrevrange(
        f"timeline:{user_id}",
        page * per_page,
        (page + 1) * per_page - 1
    )
    return fetch_tweets_by_ids(tweet_ids)  # cache hit, not DB

Reads become O(1) — just a Redis lookup. The cost moves entirely to writes. This is the fundamental tradeoff of fan-out on write: optimise for reads at the cost of writes.

The celebrity problem

Fan-out on write works beautifully until someone has 50 million followers. When Cristiano Ronaldo (hypothetically, on Twitter) posts a tweet, fan-out on write means writing to 50 million Redis sorted sets. That takes minutes — which means his followers don't see the tweet immediately, and the system is under massive write pressure for those minutes.

Twitter solved this with a hybrid approach. Users below a follower threshold (say, 1 million) use fan-out on write. Users above that threshold — celebrities, major accounts — use fan-out on read instead.

Fan-out on read for celebrities means: their tweets are not pushed to anyone's timeline cache. Instead, when you load your timeline, the system checks: do I follow any high-follower accounts? If yes, fetch their recent tweets and merge them into the pre-computed timeline from Redis. This merge happens at read time, but it's bounded — you might follow 5 celebrities, so it's 5 small fetches, not one giant fan-out.

The full read path

Putting it together, reading a timeline looks like this:

def get_timeline(user_id):
    # 1. Get pre-computed timeline from Redis (fan-out on write accounts)
    cached_tweet_ids = redis.zrevrange(f"timeline:{user_id}", 0, 19)

    # 2. Get celebrities this user follows (fan-out on read accounts)
    celebrity_follows = get_celebrity_follows(user_id)

    # 3. Fetch recent tweets from celebrities
    celebrity_tweets = []
    for celeb_id in celebrity_follows:
        tweets = get_recent_tweets(celeb_id, limit=20)
        celebrity_tweets.extend(tweets)

    # 4. Fetch full tweet objects for cached IDs
    cached_tweets = fetch_tweets_by_ids(cached_tweet_ids)

    # 5. Merge, sort by time, return top 20
    all_tweets = cached_tweets + celebrity_tweets
    return sorted(all_tweets, key=lambda t: t.created_at, reverse=True)[:20]

Storage and data flow

The write path for a normal (non-celebrity) tweet flows like this:

  • Tweet is written to the primary database (Postgres or similar) — this is the source of truth
  • A background job fans out to all followers' Redis sorted sets asynchronously
  • Tweet metadata is cached in a separate Redis hash for fast retrieval by ID
  • Media (images, video) goes to a CDN, referenced by URL in the tweet record

The fan-out job doesn't run inline with the tweet POST request — it's queued. The tweet appears in the author's own profile immediately (read from DB), and propagates to followers' timelines within seconds as the queue drains.

What about new followers?

When you follow someone, you don't immediately see their last 200 tweets in your feed — that would require backfilling your Redis sorted set with their history. Twitter's approach: after a follow, backfill the last N tweets from the new followed account into the follower's timeline cache. This is a bounded operation regardless of how prolific the account is.

The pieces you'd actually need to build this

A real implementation at scale needs:

  • A database — tweets table, follows table, users table. The source of truth. MySQL at Twitter historically; Postgres is equally valid.
  • Redis — one sorted set per user for their timeline. At 800 tweet IDs per user, this is roughly 6.4KB per user. 300 million users × 6.4KB ≈ 2TB of Redis — expensive but manageable with a Redis cluster.
  • A fan-out service — reads from a queue (Kafka, SQS, whatever), pulls follower lists, writes to Redis. This is where horizontal scaling happens — add more fan-out workers to handle write spikes.
  • A celebrity detection mechanism — a simple count on the follows table, refreshed periodically. Accounts above the threshold get a flag; fan-out workers skip them.
  • A CDN — media doesn't come from your servers. Every image and video is behind a CDN.

What this teaches you

The Twitter timeline problem is worth studying not because you're going to build Twitter, but because it's a clean example of a tradeoff that appears in almost every high-scale system: compute now or compute later. Pre-compute and cache (fan-out on write) gives you fast reads and expensive writes. Compute on demand (fan-out on read) gives you cheap writes and more work at read time.

The hybrid approach — fan-out on write for most, fan-out on read for celebrities — shows that the answer to most "which approach" questions in system design is "both, with a clear rule for which to apply when."
