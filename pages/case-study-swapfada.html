Context

SwapFada (originally called EasySwap during early development) is a Nigerian fintech application that lets users swap currencies, hold crypto and fiat wallets, and move money across the boundary between traditional and digital finance. I was brought in by the project manager — who was also building the frontend — to design and build the entire backend from scratch.

There was no existing codebase. No prior architecture. The brief was: build a production-ready backend that can handle real money, real identity verification, and real regulatory requirements in Nigeria. I was the only backend engineer on the project throughout.

The hardest part of this project wasn't any single integration. It was designing a system where every component — auth, identity, wallets, payments — had to be correct before any of it could go live. There is no "ship fast and fix later" in regulated fintech.

Architecture overview

The backend is a Django monolith with a Django REST Framework API layer. I chose this deliberately over microservices — the team was small, the timeline was tight, and the failure modes of distributed systems at this scale would have added complexity without meaningful benefit.

The application is structured around five core domains: users, identity, wallets, transactions, and notifications. Each domain is a Django app with its own models, serializers, views, and service layer. Business logic lives in services, not in views or models.

Why a service layer?

Early in the build I made the decision to introduce a services.py in each app rather than putting logic directly in views. This meant that when the Quidax webhook format changed partway through development, I only had to update one file — not hunt through view logic scattered across the codebase. For external API integrations especially, this separation paid off immediately.

KYC verification with Dojah

Know Your Customer (KYC) is a legal requirement for any financial application operating in Nigeria. Users must verify their identity before they can move money. I integrated Dojah — a Nigerian identity verification provider — to handle this.

The verification flow works as follows:

  • User submits their NIN (National Identification Number) or BVN (Bank Verification Number)
  • The backend calls Dojah's lookup API and receives identity data
  • The response is validated against what the user provided at registration
  • Verification status is recorded on the user model and the account is unlocked for transactions
# Simplified KYC verification service
class KYCService:
    def verify_nin(self, user, nin: str) -> VerificationResult:
        response = dojah_client.identity.nin_lookup(nin=nin)

        if not response.success:
            return VerificationResult(success=False, reason=response.error)

        data = response.entity
        match = (
            data.first_name.lower() == user.first_name.lower()
            and data.last_name.lower() == user.last_name.lower()
        )

        if match:
            user.kyc_status = KYCStatus.VERIFIED
            user.kyc_verified_at = timezone.now()
            user.save(update_fields=['kyc_status', 'kyc_verified_at'])

        return VerificationResult(success=match)

One challenge I didn't anticipate: name matching. Nigerian names are frequently spelled differently across documents — "Chukwuemeka" vs "Chukwu-Emeka", accents, middle names used as first names. I implemented fuzzy matching using a similarity threshold rather than strict equality, which reduced false rejections significantly.

Crypto wallet creation with Quidax

Quidax is a Nigerian cryptocurrency exchange that provides a custodial wallet API — meaning we create wallets on behalf of users, and Quidax holds the actual keys. This is the right model for a consumer fintech app where users aren't expected to manage their own private keys.

When a user completes KYC verification, the system automatically provisions wallets for the supported cryptocurrencies. This is handled as a Celery task so it doesn't block the verification response.

# Triggered after KYC verification succeeds
@shared_task
def provision_crypto_wallets(user_id: int):
    user = User.objects.get(id=user_id)
    supported = ['BTC', 'ETH', 'USDT']

    for currency in supported:
        if not Wallet.objects.filter(user=user, currency=currency).exists():
            address = quidax_client.wallets.create(
                user_id=user.quidax_id,
                currency=currency.lower()
            )
            Wallet.objects.create(
                user=user,
                currency=currency,
                address=address,
                provider=WalletProvider.QUIDAX
            )

    user.wallets_provisioned = True
    user.save(update_fields=['wallets_provisioned'])

Quidax also provides webhooks for incoming transactions. Every webhook payload is verified against a signature using the shared secret before any database writes happen — a lesson I learned from reading about exchange hacks where webhook verification was skipped.

Fiat wallet with Flutterwave

For naira deposits and withdrawals, I integrated Flutterwave. Each user gets a virtual account number — a real Nigerian bank account number that maps to their SwapFada wallet. When someone transfers money to that account number, Flutterwave sends a webhook and we credit the user's balance.

Withdrawals go through Flutterwave's transfer API, which initiates a direct bank transfer. The flow is asynchronous — the transfer is queued, Flutterwave processes it, and a webhook confirms success or failure.

The hardest part of the fiat integration was handling idempotency correctly. Webhooks can be delivered more than once. Every credit or debit operation checks for a transaction reference before writing — crediting a user twice because a webhook was retried would be a serious bug in production.

# Idempotent webhook handler
@transaction.atomic
def handle_deposit_webhook(payload: dict) -> None:
    ref = payload['data']['tx_ref']

    # Idempotency check — skip if already processed
    if Transaction.objects.filter(external_ref=ref).exists():
        return

    user = get_user_from_account(payload['data']['account_number'])
    amount = Decimal(str(payload['data']['amount']))

    Transaction.objects.create(
        user=user,
        type=TransactionType.DEPOSIT,
        amount=amount,
        external_ref=ref,
        status=TransactionStatus.COMPLETED
    )
    user.fiat_balance = F('fiat_balance') + amount
    user.save(update_fields=['fiat_balance'])

Authentication & 2FA

Authentication uses SimpleJWT with access and refresh tokens. The access token is short-lived (15 minutes); the refresh token lasts 7 days. This is standard practice for financial applications — a leaked access token has a narrow window before it expires.

Two-factor authentication uses TOTP (Time-based One-Time Passwords) — the same standard used by Google Authenticator and Authy. When a user enables 2FA, they're given a QR code to scan. On subsequent logins, after password verification succeeds, they're required to enter a valid 6-digit TOTP code before receiving their tokens.

# 2FA login flow (simplified)
class LoginView(APIView):
    def post(self, request):
        serializer = LoginSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)

        user = authenticate(
            email=serializer.validated_data['email'],
            password=serializer.validated_data['password']
        )
        if not user:
            raise AuthenticationFailed()

        if user.two_factor_enabled:
            # Issue a short-lived pre-auth token
            # Client must call /auth/2fa/verify/ next
            pre_auth = PreAuthToken.objects.create(user=user)
            return Response({'requires_2fa': True, 'token': str(pre_auth.token)})

        return Response(TokenObtainPairSerializer.get_token(user))

Key architectural decisions

  • Monolith over microservices — right choice for this team size and timeline. The domain boundaries are clear enough that splitting later is possible if needed.
  • Service layer for all business logic — views are thin, services are testable, external API clients are swappable.
  • Celery for all wallet provisioning and notifications — nothing that talks to an external API blocks the HTTP response cycle.
  • Idempotency keys on every financial write — non-negotiable. External webhooks will be delivered more than once.
  • Soft deletes on financial records — nothing is ever deleted from the transactions table. Hard deletes in financial systems create audit holes.

What I learned

Building this alone meant I had to understand every layer — not just write the code, but make every architectural decision and live with it. The things that taught me the most weren't the integrations themselves but the edge cases: what happens when a webhook arrives twice, what happens when Quidax returns an error mid-provisioning, what happens when a user's name in the NIN database is spelled differently from what they registered with.

I also learned that documentation for African fintech APIs is inconsistent. Dojah's error responses changed format between the time I read the docs and the time I integrated. Quidax's webhook documentation had gaps that I only discovered during testing. Building a robust wrapper layer around each integration — rather than calling the APIs directly from views — meant these changes were contained.

The project is currently paused at around 70% due to funding constraints. The core backend — auth, KYC, wallet provisioning, fiat deposits — is complete and tested. What remains is the swap engine, advanced transaction history, and admin tooling.
