Background

SwapFada is a Nigerian fintech application for crypto-fiat exchange. A project manager who was also building the frontend hired me to design and build the entire backend from scratch. There was no existing codebase. I was the only backend engineer throughout.

This article is about the architecture — the decisions, the tradeoffs, and the things I wish someone had told me before I started integrating with Nigerian fintech APIs.

The hardest part of building regulated fintech is not the integrations. It's designing a system where every component has to be correct before any of it can go live. There is no "ship fast and fix later" when you're handling real money.

The overall structure

The backend is a Django monolith with a DRF API layer. I chose this deliberately over microservices. The team was small, the timeline was fixed, and the failure modes of distributed systems would have added complexity without adding anything meaningful at our scale. A well-structured monolith is easier to reason about, easier to debug, and easier to deploy — and it can always be split later if the need genuinely arises.

The application is divided into five Django apps, each with a clear domain boundary:

  • users — the User model, registration, login, profile
  • identity — KYC verification, verification status, Dojah integration
  • wallets — crypto and fiat wallet models, Quidax and Flutterwave integrations
  • transactions — the transaction ledger, swaps, deposits, withdrawals
  • notifications — email and in-app notifications via Celery

Each app has its own services.py. Business logic lives in services, not in views or models. This was the single best architectural decision I made — when external APIs changed their response format (and they did), I had one file to update, not a trail of logic scattered through views.

KYC — verifying who your users actually are

Any app that moves real money in Nigeria needs KYC — Know Your Customer. Users must verify their identity before transacting. I used Dojah, a Nigerian identity verification provider that offers NIN (National Identification Number) and BVN (Bank Verification Number) lookups.

The flow: user submits their NIN or BVN → we call Dojah's API → we get back identity data → we compare it against what they provided at registration → if it matches, we mark them verified and unlock transactions.

The edge case nobody mentions in the documentation: Nigerian names are inconsistently spelled across official documents. "Chukwuemeka" in one document, "Chukwu-Emeka" in another. Strict string comparison fails too often. I implemented fuzzy matching with a similarity threshold — if the names are more than 85% similar, we consider it a match. This reduced false rejections from frustrating to rare.

from difflib import SequenceMatcher

def names_match(name_a: str, name_b: str, threshold=0.85) -> bool:
    a = name_a.lower().strip().replace('-', ' ')
    b = name_b.lower().strip().replace('-', ' ')
    ratio = SequenceMatcher(None, a, b).ratio()
    return ratio >= threshold

Crypto wallets — custodial vs non-custodial

For crypto wallets I integrated Quidax, a Nigerian crypto exchange. The key decision here was custodial vs non-custodial. A non-custodial wallet means users hold their own private keys — more control for the user, more complexity for the developer, and genuinely difficult to make user-friendly for a consumer app. A custodial wallet means Quidax holds the keys and we manage the abstraction layer.

Custodial is the right choice for a consumer fintech app. Users of SwapFada are not crypto-native — they're people who want to swap naira for USDT. They don't want to manage seed phrases. Custodial wallets mean we can give them a simple interface backed by real on-chain assets.

Wallet provisioning happens asynchronously after KYC verification completes. When a user passes KYC, a Celery task fires and creates wallets for each supported currency via the Quidax API. The user doesn't wait for this — they see a "setting up your wallets" state until the task completes.

Fiat payments — the hardest part

For naira deposits and withdrawals I used Flutterwave. Each user gets a virtual account number — a real Nigerian bank account number tied to their SwapFada account. When someone transfers money to that number, Flutterwave fires a webhook and we credit the user's balance.

Withdrawals are the reverse: we call Flutterwave's transfer API, which sends money to the user's bank account. The process is asynchronous — we queue the transfer, Flutterwave processes it (usually within seconds), and a webhook confirms success or failure.

The critical implementation detail with any payment webhook: idempotency. Webhooks can be delivered more than once. If you credit a user's balance on every delivery, you'll double-credit them. The fix is simple and non-negotiable: check for the transaction reference before writing anything.

@transaction.atomic
def process_deposit_webhook(payload: dict) -> None:
    ref = payload['data']['tx_ref']

    # If we've seen this reference, stop. Don't process twice.
    if Transaction.objects.filter(external_ref=ref).exists():
        return

    user = resolve_user_from_account(payload['data']['account_number'])
    amount = Decimal(str(payload['data']['amount']))

    Transaction.objects.create(
        user=user, type='deposit',
        amount=amount, external_ref=ref,
        status='completed'
    )
    # F() expression avoids race condition on the balance update
    user.fiat_balance = F('fiat_balance') + amount
    user.save(update_fields=['fiat_balance'])

Note the F() expression on the balance update. If two webhooks for different deposits arrive simultaneously, a normal user.fiat_balance += amount creates a race condition — both reads happen before either write. F('fiat_balance') + amount pushes the arithmetic to the database, which handles concurrent updates correctly.

Authentication and 2FA

Auth uses SimpleJWT — short-lived access tokens (15 minutes) and longer-lived refresh tokens (7 days). For a financial application, short access token lifetimes matter. A leaked access token has a 15-minute window, not a week.

2FA is TOTP — the same standard as Google Authenticator and Authy. Users scan a QR code during setup. On subsequent logins, after password verification, they enter a 6-digit code. The login flow is two steps: password → pre-auth token → TOTP code → real tokens. The pre-auth token is short-lived and single-use.

What I'd do differently

Looking back with some distance, three things I'd change:

  • Start with a proper API client wrapper on day one. I built the Dojah and Quidax wrappers partway through when I got tired of writing the same request boilerplate. Should have been first.
  • More aggressive Celery usage from the start. I moved several operations to Celery midway through when they turned out to be slow. Anything touching an external API should be in a task by default.
  • Structured logging earlier. Debugging webhook issues in development with print() statements is fine. In production, you want structured JSON logs with a request ID that you can trace across the webhook → task → database chain. I added this late.

The thing I'm most confident I got right: the service layer. When Quidax changed their webhook payload format midway through development, I updated one file. When Dojah added a new field to their NIN response, I updated one file. The views never knew any of this happened. That's the value of a service layer in an integration-heavy codebase.
